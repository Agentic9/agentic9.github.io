Architecture overview

Agentic9 Crew is a TypeScript system on Cloudflare, organised as a hexagonal architecture. The domain sits in the middle, every external concern is a port, and adapters plug in behind them. This page summarises the shape of it.

Principles

  • Hexagonal. Domain logic depends on interfaces (ports), never on Cloudflare bindings or a model vendor's SDK. Adapters implement the ports.
  • Swappable model provider. The LLM is behind LlmPort. Claude is the first adapter; open-source models via Workers AI come later without touching the domain.
  • One computer per bot. Each bot owns a persistent sandbox. Its files, shell history and browser state survive between tasks.
  • Autonomous by default, approved by exception. Tasks run to completion unless an action is marked sensitive, in which case the task suspends until a human approves.
  • Everything on Cloudflare. Workers, Durable Objects, Workflows, Queues, D1, R2, Vectorize, Sandboxes and AI Gateway. No separate servers to run.

Domain model

The core entities are deliberately few. Everything the product does is expressed in terms of these.

EntityPurpose
UserA person with an account. Owns bots, joins threads, grants approvals.
BotA named teammate with a title, description, memory, connectors and a sandbox. Descriptions drive delegation routing.
ThreadA conversation between one or more users and one or more bots. Group threads allow several bots in one place.
MessageA single turn in a thread, from a user or a bot, streamed as it is produced.
TaskA unit of work a bot has taken on. Carries state, a plan, tool calls and results. See the lifecycle below.
RoutineA scheduled or event-driven instruction, such as a 07:00 daily brief or "on every new email".
ConnectorAn authorised data connection: an OAuth integration or a custom MCP server, scoped to a bot.
MemoryWhat a bot remembers across threads: notes, embeddings and summaries it can recall later.
ApprovalA pending decision on a sensitive action. Resolved with one tap from a push notification.
ArtifactA file or output a task produced, stored in object storage and linked from the thread.

Task lifecycle

  1. queued
  2. →
  3. planning
  4. →
  5. running
  6. →
  7. awaiting_approval
  8. →
  9. done
  10. |
  11. failed

A task may loop between running and awaiting_approval as many times as it hits sensitive actions. Delegation creates a child task on another bot; the parent waits on its result.

Ports

Each port is a TypeScript interface. The domain calls the interface; an adapter provides the implementation. Swapping an adapter never changes the domain.

PortResponsibility
LlmPortChat completion with streaming and tool use. Adapters: Claude (via AI Gateway), later Workers AI.
AgentRuntimePortRuns a task's agent loop. Adapters: SandboxRuntime, Claude Managed Agents.
ConnectorPortDiscovers and invokes tools from OAuth connectors and MCP servers.
MemoryPortStores and recalls bot memory. Vector search over Vectorize, structured records in D1.
FilePortReads and writes artefacts and sandbox files. Backed by R2.
SchedulerPortRegisters and fires time-based routines. Backed by Durable Object alarms and Workflows.
TriggerPortSubscribes to external events (email, Slack, webhooks) and turns them into tasks.
NotifyPortPush notifications and other outbound messages to users.
SecretVaultPortStores connector credentials and tokens, encrypted, scoped per bot.
ApprovalPortCreates approvals, waits on them and resumes the suspended task.

Agent runtimes

Two implementations of AgentRuntimePort exist so the product is not tied to one way of executing agents.

SandboxRuntime (default)

Runs the agent loop inside the bot's Cloudflare Sandbox. The runtime drives LlmPort directly, executes tool calls in the sandbox (shell, files, browser) or through ConnectorPort, and snapshots the sandbox between tasks. Works with any LLM adapter.

Claude Managed Agents (optional)

Delegates the agent loop to Anthropic's managed agent service. The control plane still owns threads, tasks, approvals and memory, so switching runtimes is invisible to users.

Control plane

The control plane is a single Hono application deployed as a Cloudflare Worker, with state held in Durable Objects.

  • Hono Worker. HTTP and WebSocket entry point. Authentication, REST API, streaming, webhooks for triggers, and routing to the right Durable Object.
  • BotDO. One per bot. Owns the bot's configuration, connector scopes, routines (via alarms), the task queue and the handle to its sandbox.
  • ThreadDO. One per thread. Owns the message log, fan-out to participants, streaming to connected clients and delegation between bots in group threads.
  • SessionDO. One per connected client session. Holds WebSocket connections, presence and delivery of push notifications when the client is offline.

Long-running work is coordinated by Workflows and Queues so that a task survives Worker restarts. D1 holds relational data, R2 holds artefacts and sandbox snapshots, Vectorize holds memory embeddings, and AI Gateway fronts every model call for caching, logging and rate limits.
